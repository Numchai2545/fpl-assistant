วันที่บันทึก: 19 กันยายน 2026

สถานะ: พัฒนา v0.3.0 ระยะ 1–6 และ commit แล้ว ตรวจ unit/integration/UI ผ่าน ยังไม่ push/deploy

เลข v0.3.0 เป็นชื่อเป้าหมายที่เสนอ ไม่ใช่เวอร์ชันที่เผยแพร่แล้ว เอกสารนี้รวมความเห็นผู้ใช้กับผลรีวิวในบทสนทนาเดียวกัน ใช้เป็น backlog หลักของรอบถัดไป

## 2. ข้อเท็จจริงจากระบบปัจจุบัน

### ข้อมูลเก็บที่ไหน

| ตำแหน่ง | สิ่งที่เก็บ | ข้อจำกัด |
|---|---|---|
| `data/snapshots/YYYY-MM-DD/*.json` บนคอม | ข้อมูลดิบจาก FPL เช่น bootstrap, fixtures, entry, picks, transfers, ประวัตินักเตะ | gitignored; ไฟล์ชื่อเดิมถูกเขียนทับภายในวัน ไม่ใช่ประวัติทุกครั้งที่อัปเดต |
| `data/projections/` | ค่าคาดการณ์ก่อน deadline แยก timestamp | ใช้ backtest; ยังไม่ใช่ประวัติแผนที่ผู้ใช้ยืนยัน |
| `data/backtests/latest.json` เมื่อสั่งประเมินแล้ว | ผลวัดโมเดลล่าสุด | ต้องแก้การตรวจแข่งครบก่อนเชื่อผล |
| `docs/` | HTML, summary.json, ปฏิทินและไฟล์เว็บที่สร้างแล้ว | เป็นรายงานผล ไม่ใช่ฐานข้อมูลกลาง |
| Cache Storage ใน browser/PWA | สำเนาไฟล์เว็บที่ service worker เก็บ | เปิดออฟไลน์ได้ แต่ไม่ดึง FPL หรือรัน solver เอง |
| localStorage | ธีมที่เลือก | ยังไม่มีการซิงก์แผนระหว่างอุปกรณ์ |

จาก `.github/workflows/deploy-pages.yml` มีการตั้ง build/deploy เมื่อ push master, สั่ง workflow เอง และตามเวลา 09:15/21:15 น. ประเทศไทย การตั้งเวลาไม่ยืนยันว่าแต่ละรอบรันสำเร็จหรือทันเวลา ยังไม่ได้ตรวจสถานะ workflow จริงบน GitHub

workflow ปัจจุบันเผยแพร่เฉพาะ `docs/` ข้อมูลดิบและ projection ใหม่ที่สร้างบน runner ไม่ได้มีขั้นตอนบันทึกกลับเป็นคลังประวัติถาวร ต้องออกแบบ persistence เพิ่ม ไม่ถือว่าข้อมูลที่สร้างบน cloud ซิงก์กลับคอมอัตโนมัติ

### ทำไมอัปเดตมือถือไม่ได้

- ที่ localhost: หน้าเว็บ POST `/refresh` เพื่อรัน Python build แต่ client ยังใช้ cache TTL 90 นาที
- ที่ hostname อื่น: ปุ่ม fetch HTML ที่เผยแพร่ไว้ใหม่เท่านั้น ไม่มีคำสั่งเรียก FPL/build จากหน้าเว็บ
- เปิดด้วย `file:`: ปุ่มอัปเดตถูกซ่อน
- server บนคอม bind `127.0.0.1` จึงไม่ใช่บริการสำหรับมือถือโดยตรง
- GitHub Pages เป็น static hosting; frontend เดิมจึงไม่มี Python backend ที่เรียกได้ตามกด
- เส้นทางที่ผู้ใช้เปิดจริงบนมือถือยังรอ URL/ที่มาของไอคอน PWA เพื่อยืนยัน ไม่สรุปว่า workflow ล้มเหลวโดยไม่มีหลักฐาน

### โมเดลดูฟอร์มอย่างเดียวหรือไม่

ไม่ใช่: `model.py` ใช้ xG/xA, นาทีลงเล่น, คู่แข่ง, เหย้า/เยือน, clean sheet, bonus ฯลฯ แล้วผสม recent form ตาม config 15% คำแนะนำซื้อขายดู 5 นัดจริงถัดไป และ solver วาง 6 GW แต่หน้าเว็บยังอธิบายอิทธิพลแต่ละส่วนไม่ชัด

การมีตัวรุกและตัวรับคนละฝั่งไม่ได้มีบทลงโทษพิเศษเพราะถือทั้งคู่ หากตัวรุกยิงขณะตัวรับยังเล่นอยู่ ตัวรับอาจเสีย clean sheet ส่วนตัวรุกได้คะแนนตามเหตุการณ์ ไม่ใช่เอาคะแนนสองคนมาหักกันโดยตรง ตัวรับที่ออกหลังเล่นครบเกณฑ์ก่อนเสียประตูมีข้อยกเว้นเรื่อง clean sheet

ในเชิงคณิตศาสตร์ ผลรวม expected points ยังบวกกันได้แม้ผลลัพธ์สัมพันธ์กัน ความสัมพันธ์มีผลต่อการกระจายผลลัพธ์/โอกาสทำคะแนนพร้อมกัน จึงควรแสดง trade-off และทดสอบความเสี่ยง ไม่หัก EP เพิ่มเพียงเพราะเจอกันจนเป็นการนับผลเสียซ้ำ

### ทำไมแผนเปลี่ยน

ระบบแก้ปัญหาใหม่ทุก build ตามข้อมูลล่าสุด แต่ยังไม่มีแผนที่ผู้ใช้เลือกเป็นฐานและไม่มี change log แผนใหม่อาจเกิดจากข้อมูลเปลี่ยนจริง คะแนนใกล้กัน หรือ solver ได้คำตอบใกล้เคียงกัน ต้องแยกสาเหตุด้วยหลักฐาน ไม่สรุปว่าทุกการเปลี่ยนมาจากฟอร์มหรือเป็นบั๊ก

## 4. ขอบเขตผลิตภัณฑ์ v0.3.0

### A. อัปเดตข้อมูลจากมือถือได้จริง

1. แยกการขอข้อมูลสดออกจากงาน solver; แสดงข้อมูลทีม/ผลแข่งที่ดึงเสร็จก่อน แล้วแสดงสถานะกำลังวิเคราะห์
2. ปุ่มอัปเดตต้องสร้างงานบน backend หรือ gateway ที่สั่ง worker ได้ ไม่เพียง reload HTML
3. ออกแบบสถานะ queued/fetching/analyzing/ready/partial/failed พร้อม request ID, เวลา, เหตุผล และ retry โดยไม่เผยแพร่ผลครึ่งชุด
4. Manual refresh bypass cache สำหรับทีม, transfers, fixtures, คะแนนและ availability ที่จำเป็น; ใช้ cache แยกตามประเภทข้อมูลและ team ID พร้อม deduplicate งานซ้ำและ backoff
5. แยก “GW ปัจจุบัน: คะแนนระหว่างแข่ง” กับ “GW ถัดไป: วางทีม” บอกยังไม่เริ่ม/กำลังแข่ง/จบเกม/ผลยืนยันแล้ว ไม่เรียกคะแนนยังไม่สมบูรณ์ว่าผลสุดท้าย
6. สำรวจ live endpoint และเวลาที่ public entry/transfers เปิดเผยข้อมูลจริงก่อนรับรองการซิงก์หลังย้าย ถ้าต้นทางยังไม่เปิดเผย ต้องบอกตรง ๆ และให้บันทึกการย้ายที่ผู้ใช้ยืนยันเองเป็น overlay ที่มีป้ายชัดเจน
7. Overlay ต้องเก็บ provenance, เวลายืนยัน, งบ/FT ที่ยืนยัน และ reconcile เมื่อ API ตามทัน โดยไม่หักเงินหรือ FT ซ้ำ ไม่ใช้ FPL login/password หรือทำรายการแทนผู้ใช้
8. เป้าหมาย UX เบื้องต้น: รับทราบคำขอทันที แสดงข้อมูลพื้นฐานก่อน solver; วัด p50/p95 จากการทดลองก่อนตกลง SLA ไม่สัญญาข้อมูลทันทีหาก FPL ยังไม่เผยแพร่หรือระบบถูกจำกัดอัตรา
9. ถ้าออฟไลน์/API ล้มเหลว ให้แสดงข้อมูลล่าสุดที่สำเร็จและอายุจริง ห้ามเปลี่ยน timestamp ต้นทางเป็นเวลาปัจจุบัน

### B. เปรียบเทียบการย้ายหลายตัว

1. ทุกครั้งมี baseline “ไม่ย้าย” และแผน 1, 2, … จนถึง FT ที่มี โดยปกติสูงสุดตามกติกาที่ตรวจสอบ; แผนเสียแต้มเป็นหมวดแยกและไม่เลือกให้อัตโนมัติ
2. แสดงแผนเด่นจำนวนพอดี เช่น 3–5 ชุดที่แตกต่างกันจริง พร้อมขยายดูจำนวนย้ายอื่น ไม่แสดง permutation ของชุดเดียวกันเป็นคนละทางเลือก
3. คำนวณเป็นชุดเดียว: ขายตัวหนึ่งปลดงบให้อีกตำแหน่งได้ ตรวจเงินสด ราคาขาย ตำแหน่ง จำนวนต่อสโมสร และ FT/hit รวม ห้ามรวมอันดับการย้ายเดี่ยวเข้าด้วยกันโดยไม่แก้งบใหม่
4. เปรียบเทียบคะแนน XI+กัปตัน+สำรองตามสมมติฐานเดียวกันบนช่วง GW ร่วมกัน แสดง GW ถัดไปและผลรวม horizon; โปรแกรม 5 นัดรายคนเป็นข้อมูลประกอบ ไม่ใช้หน้าต่างเวลาต่างกันเป็นตัวตัดสินชุดแผน
5. แสดงประโยชน์ส่วนเพิ่มของตัวที่สอง/สาม และโอกาสเสีย FT จากการใช้ตอนนี้ ไม่ตั้ง threshold สำหรับชุดใหม่ด้วยการคูณ 3.0 แบบไม่มีการตรวจสอบ
6. เลือก candidate เอง, ล็อกไม่ขาย, ตัดคนไม่สนใจ และเลือกความยืดหยุ่นงบได้; ทุกการเปลี่ยนคำนวณ XI/C/V/bench/เงิน/FT ใหม่ใน scenario
7. แยกการ “เลือกแผนจำลอง” จาก “ผู้ใช้ยืนยันทำรายการแล้ว”; ไม่ถือว่ากดเลือกแผนคือซื้อขายใน FPL

### C. เหตุผลการเลือกและโปรแกรม

1. การ์ดเหตุผล: นาทีคาดการณ์, โอกาสลง, ฟอร์ม, คู่แข่งเหย้า/เยือน, attacking/clean-sheet/other EP, ผลต่างกับตัวเดิม และช่วงเวลาที่ใช้คำนวณ
2. แสดง EP ราย GW, fixture จำนวนจริง, blank/double และวันเริ่มเตะ เพื่อเห็นว่าเลือกเพื่อสัปดาห์นี้หรือระยะยาว
3. แสดงป้ายตัวรุกชนแนวรับที่ผู้ใช้ถือ พร้อมทางเลือกจัดตัวและผลรวมคะแนน; ไม่ห้ามคู่แข่งอยู่ร่วมทีมเป็นค่าเริ่มต้น
4. หากเพิ่มโหมดลดความเสี่ยง ต้องระบุว่าเป็น preference หรือแบบจำลองความสัมพันธ์ที่ยังต้องตรวจสอบ ไม่แสดงช่วงความเชื่อมั่น/โอกาสชนะที่ไม่มีการ calibrate
5. ทดสอบความไวต่อ form weight และ availability; ห้ามใช้สถานะเจ็บ “นัดถัดไป” เป็นข้อสรุปแน่นอนตลอด 6 GW โดยไม่แสดงสมมติฐานการฟื้นตัว

### D. แผนระยะยาวที่ติดตามได้

1. เก็บ selected plan และ plan versions แบบถาวร อ้าง snapshot/model/config/solver version, season, team และเวลา
2. ทุก refresh เปรียบเทียบแผนเดิมกับข้อมูลใหม่ก่อนเสนอเปลี่ยน แสดงคนเข้าออก คะแนนต่าง งบ/FT ต่าง และเหตุผลจากข้อมูลที่เปลี่ยน
3. ใช้ tie-break ที่แน่นอนสำหรับแผนคะแนนเท่ากัน พร้อม change threshold ที่ตรวจสอบได้ ลดการสลับเพราะส่วนต่างเล็กมาก
4. แผนผิดกติกาหรือมีข่าวสำคัญต้องแจ้งทันที ไม่รักษาแผนเก่าเพื่อให้ดูนิ่ง; การปรับตามข่าวจริงเป็นพฤติกรรมที่ต้องมี
5. แยก “การตัดสินใจก่อน deadline นี้” กับ “แนวทาง GW หลัง ๆ” และเงื่อนไขที่จะทำให้แผนเปลี่ยน
6. Refresh live score ไม่รัน/เปลี่ยนแผนระยะยาวทุกครั้งโดยปริยาย; ให้ผู้ใช้รู้ว่ากำลังดูคะแนนสดหรือกดวิเคราะห์แผนใหม่

### E. ประวัติข้อมูลและการประเมินโมเดล

1. เก็บ snapshot ตามเวลา/version แทนเขียนทับรายวัน พร้อมแยก source event และ season; แชร์ข้อมูลลีกแต่แยกข้อมูล entry
2. เก็บแผนและความคิดเห็นผู้ใช้บนแหล่งข้อมูลกลางที่เลือก เพื่อเปิดมือถือ/คอมเห็นแผนเดียวกัน
3. เก็บ projection ก่อน deadline แบบ immutable และผลแข่งที่ยืนยันแล้ว; มีจำนวน pending/missing และเลือก policy projection ต่อ GW ให้ชัด
4. ประเมินทั้ง prediction MAE/bias เทียบ captured FPL baseline และผลของคำแนะนำทีม/กัปตันโดยไม่ใช้ข้อมูลอนาคต
5. เก็บ config/model version และจำนวนตัวอย่าง ไม่สรุปผลดีขึ้นจากเพียงหนึ่ง GW; แยกการเปลี่ยนโมเดลจากการเปลี่ยนข้อมูล
6. กำหนด retention, backup/restore และย้ายข้อมูลเดิมโดยรักษาประวัติ ไม่ลบ snapshot ของผู้ใช้

## 5. สถาปัตยกรรมที่เสนอและจุดตัดสินใจ

เส้นทางเป้าหมาย: มือถือ/คอม → บริการรับคำขอ → งานดึง FPL → snapshot ที่มีเวอร์ชัน → งานวิเคราะห์ → ผลลัพธ์พร้อมสถานะ → หน้าเว็บ

ทั้ง local และ cloud ควรใช้ data contract และ analysis core ร่วมกัน เพื่อให้ข้อมูลชุดเดียวกันสร้างคำตอบสอดคล้องกัน

| ทางเลือก | เหมาะกับอะไร | ข้อแลกเปลี่ยน |
|---|---|---|
| A: backend + worker + persistent storage | เป้าหมายใช้งานมือถือขณะคอมปิด อัปเดตตามกดและเก็บแผนข้ามอุปกรณ์ | ต้องเลือกผู้ให้บริการและงบ ตรวจข้อจำกัดการรัน CBC/งานยาวและต้นทุนก่อนเลือก |
| B: Pages + secure gateway เรียก Actions | ทางประหยัดที่ใช้ระบบเผยแพร่เดิมต่อ | ต้องมี gateway/สถานะงาน/ที่เก็บประวัติ; มีเวลาคิวและ deploy ไม่ใช่ live refresh ที่รับประกันได้ |
| C: ใช้คอมเป็น server ผ่านช่องทางส่วนตัว | ไม่มีงานวิเคราะห์บนโฮสต์ภายนอก | คอมต้องเปิดและเชื่อมต่อ; ไม่ผ่านโจทย์มือถือใช้งานอิสระเมื่อคอมปิด |

ผู้ใช้ยืนยันว่าเน้นฟรีก่อนและยอมรอประมวลผลได้ จึงใช้ B เป็นแนวทางตั้งต้น: เก็บ Pages เป็นหน้าเว็บ ใช้ secure gateway บนบริการที่มี free tier เพื่อสั่ง Actions พร้อมแสดงสถานะคิว/ดึงข้อมูล/วิเคราะห์/เผยแพร่ ต้องตรวจ quota, การยืนยันผู้ใช้, persistence และเงื่อนไข free tier ก่อนเลือกผู้ให้บริการ ไม่รับรองว่าฟรีถาวรหรือใช้เวลาแน่นอน ทาง A เป็นทางเลือกในอนาคตหากข้อจำกัด B ไม่ผ่านการตรวจรับ ไม่ใช่ข้อเสนอให้ซื้อโฮสต์ตอนนี้

คำว่าอัปเดตในเวอร์ชันนี้หมายถึงกดเริ่มงานดึงข้อมูลใหม่ได้จากมือถือและรอผล ไม่ใช่ streaming คะแนนตลอดเวลา หาก free tier ไม่รองรับ gateway ให้ประเมินทางเลือกสั่ง workflow ผ่าน GitHub ที่ผู้ใช้ล็อกอินเอง โดยอธิบายขั้นตอนเพิ่มก่อนเปลี่ยน UX; ห้ามแก้ด้วยการฝัง token ในหน้าเว็บ

ไม่วาง token สำหรับสั่ง workflow หรือ secret ของบริการไว้ใน HTML/JavaScript/PWA ใช้ session ของบริการที่เหมาะกับแอปส่วนตัว จำกัดการเรียกงานและแยกสิทธิ์อ่านกับสั่งประมวลผล ไม่เกี่ยวกับการล็อกอิน FPL

GitHub Actions schedule เป็น fallback ได้ แต่ไม่ควรเขียนว่ารายงาน “เก่าไม่เกิน 12 ชั่วโมง” โดยไม่มีการติดตามความสำเร็จ เนื่องจากงานตามเวลาอาจล่าช้า

## 6. ลำดับดำเนินงานเมื่อได้รับคำสั่งให้เริ่ม

| ระยะ | งาน/สิ่งส่งมอบ | เงื่อนไขผ่านก่อนเดินต่อ |
|---|---|---|
| 0 — ยืนยันเส้นทางข้อมูล | ยืนยัน URL มือถือ/งบ; ตรวจ API เรื่อง transfers หลังทำรายการและ live scores; ตรวจ cloud workflow จริงแบบอ่านอย่างเดียว; เลือก architecture พร้อมประมาณต้นทุน | รู้ว่าข้อมูลใดดึงสดได้/ไม่ได้ และมีแผนสำหรับข้อจำกัดต้นทาง |
| 1 — ความถูกต้องพื้นฐาน | แก้ R1/R2/R6/R7; data contract + provenance; atomic publication; validation ผล solver รวม timeout/no incumbent | ทีมไม่ทราบ/ข้อมูลบางส่วน/solver ไม่สำเร็จต้องไม่สร้างคำแนะนำที่ดูเหมือนสมบูรณ์ |
| 2 — อัปเดตข้ามอุปกรณ์ | backend/gateway, status, storage, refresh, current-GW live view, manual-confirmed overlay/reconcile เมื่อจำเป็น | มือถือขณะคอมปิดขอข้อมูลใหม่ได้ตาม architecture; แสดง source freshness และเก็บประวัติข้าม restart |
| 3 — scenario engine | baseline + หลายจำนวนย้าย + alternatives + เลือก candidate/locks; งบ FT/hit และคะแนนช่วงเดียวกัน | ทุกชุดถูกกติกา มี baseline และประโยชน์ส่วนเพิ่มชัดเจน |
| 4 — ความต่อเนื่องและเหตุผล | saved plan/change log, tie-break, change threshold, EP breakdown, โปรแกรมและคู่แข่งในทีม | อธิบายได้ว่าแผนเปลี่ยนเพราะอะไร และไม่เปลี่ยนแผนที่เลือกโดยเงียบ ๆ |
| 5 — หน้าเว็บและเอกสาร | ทีมจริง/จำลอง, deadline/C/V, modal/filter/keyboard/mobile, ข้อมูลเก่าหรือออฟไลน์; ปรับ README/CLAUDE/config comments ให้ตรง | ใช้งานบนมือถือจริงครบเส้นทาง; เอกสารไม่มีข้อกำหนดหนึ่ง transfer หรือ local-only ที่ขัดกับเวอร์ชันใหม่ |
| 6 — ตรวจรับก่อนเผยแพร่ | regression, API integration, mobile/PWA, timeout/offline, backup/restore, migration และ rollback rehearsal | ผ่านรายการตรวจรับด้านล่างและให้ผู้ใช้ทดลองผลที่ review ได้ก่อน release |

ทำได้เป็น milestone ภายใน แต่รวมเป็น release v0.3.0 ตามขอบเขตที่ตกลง ไม่เปลี่ยนเวอร์ชันหรือ deploy ระหว่างขั้นวางแผน

## 7. รายการตรวจรับ

- [ ] มือถือกดอัปเดตส่งคำขอใหม่จริง ไม่ใช่ HTML reload; ไม่ต้องเปิดคอมเมื่อเลือก A/B
- [ ] ต้นทางยังไม่เผยแพร่ transfers ต้องขึ้นสถานะรอ/ให้ยืนยันเอง ไม่แอบใช้ทีมเดิมว่าซิงก์แล้ว
- [ ] หลังยืนยันการย้ายเองแล้ว API ตามทัน ไม่บันทึกซ้ำ งบและ FT ไม่ถูกหักสองครั้ง
- [ ] แสดง GW ปัจจุบันกับ GW ถัดไปถูกต้องทั้งก่อน/หลัง deadline ระหว่างแข่งและหลังจบครบ
- [ ] ข้อมูลเดิม input/model/config เดิมได้แผนเดิมหรือแสดงเหตุผล solver กรณีไม่ยืนยัน optimum; ไม่มีผล fractional ถูกแสดงเป็นทีมจริง
- [ ] FT 0/1/2/5, ย้ายแล้วบางส่วน, hit, chip, ซื้อกลับใน GW เดียวกัน และขายสองคนปลดงบให้กัน ถูกคำนวณตามกติกาที่ตรวจสอบ
- [ ] รายการ chip/FT และทีมหลัง Free Hit ต้อง reconcile กับสถานะจริง ไม่ใช้ picks ชั่วคราวเป็นทีมถาวรโดยไม่ตรวจ
- [ ] baseline และแผน 1/2/หลายตัวใช้ horizon เดียวกัน ผลต่างไม่มาจากการนับแมตช์/bench/captain คนละแบบ
- [ ] เลือกทางเลือกใดแล้วสนาม เงิน FT และกัปตันตรงกัน ไม่มีการส่งคำสั่งเปลี่ยนทีมไป FPL
- [ ] เปิดมือถือ 320/390px เห็น deadline/C/V; EP ใน comparison เข้าถึงง่าย; sort ใช้ชุดข้อมูลครบและ keyboard ไม่หลุดหลัง modal
- [ ] ออฟไลน์/timeout/429/ข้อมูลบางส่วน/refresh ซ้อน/ปิดหน้าแล้วกลับมา ต้องมีสถานะชัดและไม่ทำลายรายงานที่สำเร็จล่าสุด
- [ ] saved plan ยังอยู่เมื่อเปลี่ยนอุปกรณ์/restart/deploy และกู้คืนจาก backup ได้
- [ ] backtest ไม่นับคะแนนระหว่างแข่งเป็น final; DGW/blank/เลื่อนแข่ง/missing history มีสถานะที่ถูกต้อง
- [ ] ทดสอบที่จำเป็นกับ logic ใหม่และ regression เดิม พร้อมทดลองเส้นทางผู้ใช้จริง ไม่ใช้จำนวน unit tests อย่างเดียวรับรองคุณภาพ

## 8. ยังต้องยืนยัน / ไม่รวมในคำสั่งปัจจุบัน

- ผู้ใช้ยืนยันว่าเปิดเว็บแล้ว Add to Home Screen: ต้องตรวจรับทั้ง browser และ PWA ที่ติดตั้ง รวม service-worker update และ cache เดิมหลัง deploy
- ผู้ใช้ยืนยันว่าเน้นฟรีก่อน ยอมรอประมวลผลได้: เลือก B เป็นแนวทางตั้งต้น และไม่สมัครบริการเสียเงิน
- ยังไม่มี URL ที่เปิดจริง จึงทราบวิธีเปิดว่าเป็น Add to Home Screen แต่ยังไม่ยืนยัน hostname; ตรวจ URL เมื่อเริ่มระยะ 0 โดยไม่ขวางการวางแผนส่วนอื่น
- ไม่มีการเปิดบัญชีบริการ ซื้อโฮสต์ เปลี่ยน GitHub settings ส่งข้อความไปบุคคลอื่น หรือ deploy ในรอบนี้
- ไม่มี FPL authentication, การซื้อขาย/จัดตัว/เล่น chip อัตโนมัติ หรือรับรองว่าโมเดลแม่นกว่า FPL
- ไม่สัญญาเวลาจบงานเป็นจำนวนวันก่อนยืนยันเส้นทางข้อมูลและ infrastructure; แบ่งความคืบหน้าตาม milestone ที่ตรวจรับได้
- เพิ่มความคิดเห็นผู้ใช้ต่อท้ายพร้อมวันที่ และปรับ requirement/acceptance criteria ที่เกี่ยวข้องก่อนเริ่มงาน
